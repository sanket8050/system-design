## Day 35: Consumer-Side Deduplication Strategies

Since message brokers typically guarantee at-least-once delivery, consumers must implement strategies to handle duplicate messages. This is often called *consumer-side deduplication*.

### The Core Idea: Unique Identifiers

The most common approach is to assign a unique identifier (often called an `idempotencyKey`, `requestId`, or `messageId`) to each logical operation or event. This ID should be generated by the *producer* of the message/request and passed along with the payload.

### Strategy 1: Storing Processed IDs

1.  **Generate Unique ID:** The client/producer generates a globally unique ID (e.g., UUIDv4) for each *business transaction*.
2.  **Pass ID:** This ID is included in the message payload or HTTP request header.
3.  **Consumer Logic:** When a consumer receives a message:
    a.  Extract the `idempotencyKey`.
    b.  Check a durable store (database table, distributed cache like Redis, or even a dedicated idempotency service) to see if this `idempotencyKey` has already been processed.
    c.  If processed, ignore the message (it's a duplicate).
    d.  If not processed, execute the business logic.
    e.  **Crucially:** After successful business logic execution, store the `idempotencyKey` in the durable store, marking it as processed.

### Handling Race Conditions (Check-Then-Act)

The "check if processed, then process and store" pattern is vulnerable to race conditions in concurrent environments. If two instances of the consumer (or two retries) receive the same message simultaneously, both might check, find no record, and attempt to process.

**Solutions:**

1.  **Transactional Approach (Database):** Combine the check and the store operation within a single database transaction. When processing a message:
    *   `BEGIN TRANSACTION`
    *   `SELECT id FROM processed_messages WHERE idempotency_key = ? FOR UPDATE;` (using a row-level lock)
    *   If found, `ROLLBACK`.
    *   If not found, execute business logic, then `INSERT INTO processed_messages (idempotency_key, status) VALUES (?, 'completed');`
    *   `COMMIT`
    This ensures atomicity of the check-and-store, preventing duplicates at the database level.

2.  **Distributed Lock (Redis):** Acquire a distributed lock using the `idempotencyKey` before processing. If the lock cannot be acquired, another process is already handling it. Release the lock after processing.
    *   This is simpler but adds external dependency and requires careful handling of lock expiration.

3.  **Unique Constraint:** The simplest database approach is to have a unique constraint on the `idempotencyKey` column in your `processed_messages` table. If an `INSERT` fails due to a duplicate key, you know it's already processed.
    *   `INSERT INTO processed_messages (idempotency_key, status) VALUES (?, 'processing') ON CONFLICT (idempotency_key) DO NOTHING;` (or `DO UPDATE` if you track status).
    *   If the insert succeeds, proceed with business logic. If it conflicts, assume another process is handling or has handled it.

### Idempotency Key Expiration

Processed `idempotencyKey`s can accumulate. Implement a TTL (Time-To-Live) or a cleanup job for keys after a reasonable period (e.g., 7-30 days), assuming messages older than this won't be redelivered.
